### What the analysis found — all four sub-threads are genuine gaps

1. **Agent/consumer registration — genuine gap, and foundational.** Every ingress control in Phases 1–4 authenticates the *human*. Nothing authenticates the *software* holding the session. 02 §4.8 ("the gateway is the only door") is entirely about **egress**; ingress is undefended. Three concrete consequences: `consumption_edge` and `/activity/consumption` had **no authenticated source** for "consuming agent" (so G9 @ M1 was not honestly evidenceable); Dynamic Client Registration was undecided, which would have made the set of permitted software the only unreviewable grant in the system; and Wave 0 exit criterion 5 evidenced only half a door.
2. **Consumer-level governance/usage tracking — genuine gap.** 01 G4 @ M2 promises security-anomaly monitoring at Wave 3 with **no mechanism in Phase 2, no screen in Phase 3, no task in Phase 4**. All rate/quota controls are keyed `(human, tool)`; nothing bounds one consumer across tools. Idempotency suppresses identical repeats, not forty *different* vouchers in four minutes.
3. **Binding-type-aware execution authorization — genuine gap, exactly as the user described.** Binding type already drives the handshake, the review path, the sandbox harness and the database-read-only rule — but three of those are **design-time** and the two runtime gates are keyed on *scope* and *sensitivity*, never on binding type. So once a `plsql`/`function` tool is in a role's scope, any session holding that role fires it as easily as a REST read. `forge.invoke` deliberately bypasses listing and was re-checked only against scope.
4. **Credentials/secrets — genuine gap.** Two sentences about a secret store and no design: no store choice, no ref format, no rule on who may resolve a ref to a value, no rotation policy, no blast-radius containment, no revocation path. `overlay-purity` checked file *types*, not content, so a pasted password would have passed CI.

### The core design decisions taken

- **Consumer Registry as a second principal.** `kind: Consumer` is a **git artefact** in `consumers/`, so registration reuses the existing change-proposal → approval → merge flow and needs no new governance machinery. **Admin-approved; self-service and RFC 7591 DCR are disabled** (with a legible 403, not a silent 404). The composition rule: *authorization is the **intersection** of what the consumer may do and what the human may do — never the union, never a substitute.* Checked twice: step `[2a]` at session establishment (refused at `initialize`, no `tools/list` served) and stage `6a′` per call. Suspension rides the **existing kill switch, extended from four granularities to five** (consumer joins). `visible(session)` becomes a **six-way** intersection. `humanInTheLoop: false` forces `humanApprovalRequired` on every write.
- **New policy-chain stage `6e′` — binding-type authorization,** placed after `6e` (sensitivity ceiling) and before `6f`/`6g` so no plan token is ever minted without the grant. **Two postures:** standard (`rest`, read-only `database`, read-only `wrapped-vendor`) is default-allow within scope; **elevated** (`plsql`, `function`, write-classified `wrapped-vendor`, and anything carrying a `policyException`) requires an **explicit, named, expiring, approval-recorded `bindingGrant`** — scope membership alone is never sufficient — plus forced approval on writes, `humanInTheLoop: true`, tighter anomaly thresholds and 180-day expiry. `standingAuthorization` (a recorded, expiring approval record) is the hinge that keeps this implementable: it substitutes a standing approval for a per-call one and **removes nothing else**.
- **`database` read-only-by-policy is NOT subsumed** — it sits alongside (validate-time structural rule vs runtime authorization; and `database` is already the most caged binding, so an elevated grant would be ceremony). **One extension:** any tool carrying a `policyException` is elevated posture regardless of binding type.
- **IA decision: no new top-level route.** Nine destinations stand. **Governance gains a fifth tab (`Consumers`)** — the registry, following the Roles tab's compiled-artefact pattern; **Activity gains `/activity/consumers`** — usage, quotas, detectors, anomaly events. The rule: *Governance is where a consumer's authorization is decided; Activity is where its behaviour is observed. Registration is a grant; usage is an event.* Mirrors the plan's own definitional/runtime and git/store split.
- **`SecretStore` as the third pluggable seam** after `IdentityProvider` and `ChangeHost`. `secretRef://<scope>/<subject>/<purpose>` is the only form a credential ever takes anywhere visible. W0: `EncryptedFileStore` (sealed file, OS-keychain key) + `OsKeychainStore`, both under one contract suite — the `W0-C5`/`W0-D3` precedent. `OciVaultStore` is the named production target and is **not** a W0 dependency. One credential per (binding × module × environment). Confirm-token HMAC rotates with a **dual-key overlap window** so rotation does not void in-flight plan tokens. `forge secrets revoke` invalidates **and** kill-switches dependents in one act.
- **"No service-account fallback" — CONFIRMED, not corrected.** The principle is about **substitution**, not storage. Made explicit as a **four-part test**: (1) the binding structurally cannot carry per-user identity *per the probe*; (2) a per-user identity is still resolved and a missing mapping is still a hard failure; (3) a named compensating control carries it into the target and is echoed to audit; (4) the credential is scoped to one module and one environment. Fail any part → it is a service-account fallback and is forbidden. **All four are checkable from data the system already holds**, so it becomes a `forge validate` rule and a privilege-escalation case rather than a paragraph.

## The wave-boundary pause — the mechanism, because it is the point

Three independent locks, all required:
1. **`Select-NextTask` is wave-scoped** — Wave 1 tasks are invisible to a Wave 0 run. The driver cannot cross by accident because it cannot see across.
2. **On wave completion it writes `docs\build-plan\WAVE_<N>_CHECKPOINT.md` pre-filled** with agenda items 1 (each of Phase 1 §7's exit criteria, now 14 of them, with the tasks meant to satisfy it and their state), 2 (the latest `forge bench` metrics), 6 (the intervention log and the unassisted-completion rate) and 8 (time and token cost), leaving items 3, 4, 5 and 7 headed and empty because they are judgment — and `verdict:` unfilled at the top. Then it halts with exit code 10.
3. **Crossing in needs two independent human acts:** a filled, recognised `verdict:` line in the previous wave's checkpoint **and** `-AcknowledgeWave <N>` on the command line. A `STOP-AND-FIX` verdict is refused regardless of the flag.

In-wave human gates work the same way at smaller scale (exit code 11 + a `NEEDS-DECISION-<id>.md`). Wave 0 has **eight** human gates (seven original + `W0-HG8` added by Phase 5).

## The datastore correction — what Phase 2 assumed that SQLite cannot do

Applied as `02_TECHNICAL_ARCHITECTURE.md` §10, with inline SUPERSEDED markers on §1.5, §1.2's persistence/tests rows, §1.6 items 1/2/4, §6.6's topology box and §9 judgment call 4. The git/datastore split holds and is cleaner under SQLite — definitions in git, events in the store, and `rm -rf .mcpforge/` must leave a fully working system (now a test, `W0-C6`).

Eight items named, none silently dropped. Two of them change what may honestly be claimed:

1. **Audit immutability — the one genuine loss.** §4.6 assumed `UPDATE`/`DELETE` revoked at the database. SQLite has no users, roles or grants at all. Wave 0 substitutes append-only triggers + the `prev_hash`/`row_hash` chain + file permissions. On SQLite immutability is *detectable*, not *preventable* — anyone with the file can drop the triggers and rewrite a row; the chain will then fail verification, but the write is not prevented. Consequences: `forge audit verify` is load-bearing at Wave 0, not a nicety; and the Wave 0 checkpoint must record this as an accepted waiver with a named closure trigger (the Postgres migration), not pass exit criterion 7 silently. **Phase 5 consequence — this is operational flag (a) above: because the hash chain is the only integrity mechanism, its schema must be complete before the first row, so `W0-C2` must carry the consumer/credential columns rather than a later migration.**
2. **No multi-replica gateway at Wave 0.** §4.8 said plan tokens work across replicas because their nonces live in a shared database. SQLite is single-writer/single-host, so the gateway runs as one instance and no exit criterion may be evidenced as if multi-replica works. The security property survives (single-use nonce via a `UNIQUE` insert in the same transaction as the execute, atomic on one node); only the scaling property is deferred.
3–8. GIN index, array columns, `gen_random_uuid()`, `jsonb` operators, concurrent writers, and Testcontainers CI all handled without loss — see full detail in the doc itself if needed; window functions and CTEs are not Postgres-specific and needed no change.
